## Explanation / Analysis

### What this document is about

The document is a **cloud compute abstraction ladder**: a top-to-bottom progression from the least abstract (most control) to the most abstract (least control) way of running workloads in the cloud. Each tier lists representative providers and briefly states what you manage vs. what the platform manages.

### Structure and progression

- **IaaS (Infrastructure as a Service)**  
  You get VMs; you manage OS, runtime, scaling, and most of the stack. Examples: AWS EC2, Azure VMs, Google Compute Engine.

- **CaaS / Container Orchestration**  
  You run containers; the platform handles orchestration, services, scaling, and networking. Kubernetes (EKS, GKE, AKS, OpenShift), ECS, and Nomad are in this tier. Docker is called out as the **enabler** (tooling/runtime) for containers, not a service layer itself—it sits conceptually here because CaaS platforms build on container tech like Docker.

- **PaaS (Platform as a Service)**  
  You deploy an app or image; the platform handles infrastructure, scaling, and routing. Examples: AWS App Runner, Heroku, Google App Engine, Azure App Service.

- **FaaS / Serverless**  
  You deploy functions; the platform runs and scales them per event. Examples: AWS Lambda, Azure Functions, Google Cloud Functions, Cloudflare Workers.

### How the parts relate

- **Vertical arrows (↓)** indicate increasing abstraction: each step removes more operational responsibility from you and gives more to the platform.
- **Mental model**: moving down the list trades control for simplicity and managed operations; moving up trades simplicity for control and customization.
- There are no sensitive values or secrets in the content; nothing is redacted.

### Purpose

The note is a quick reference for comparing cloud compute tiers and placing specific products (including Docker) on that ladder. It is useful for choosing the right abstraction level for a project or for explaining the cloud stack to others.
